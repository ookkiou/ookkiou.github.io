### BPE 分词方法

在训练的时候，我们会给出词表大小。还会有 256 个初始字节，和几个特殊字例如 <'endoftext'>。之后预分割按照空格，再拆分成字节，按照字节对的频率合并，每合并一次，词表多一个 token。直到词表大小满足我们的设定。 在正式使用时，我们已经有了完整的词表。用户输入出来文本的时候呢，我们先编码，就是 Encoder，还是按照 BPE 的基本思路把它切分成单个字节，然后我们按照频率合并，对照词表查找 token id，发送给模型。模型生成 token id 之后，使用 decode 解码，查表把所有 token 还原成字节串拼接到一起，然后解码输出。

BPE 不会出现"token 不在词表里"的情况 。因为初始词表就是 256 个字节，覆盖所有 UTF-8 编码。编码时"能合并就合并，合不了就留字节"——最坏退化成纯字节序列，永不失败。代价是生僻内容占更多 token、模型学得差，但这是"能用但差"，不是 OOV 失败。这正是 ByteLevel 取代传统 tokenizer 的核心原因： 用 256 字节兜底一切，用 BPE 合并提升效率 。

### minimind 的分词策略



传统的 BPE 会预切分，按照空格先把文本切成单词，而中文没有空格可以切。 所以 minimind 使用 ByteLevel BPE 所有语言走同一套机制： ByteLevel 的做法 ：跳过"按空格切词"这一步，直接把 所有文本先转成 UTF-8 字节序列 ，在字节层面做 BPE。

* 英文 hello → UTF-8 字节 [104, 101, 108, 108, 111] （5 字节，每字符 1 字节）
* 中文 你好 → UTF-8 字节 [228, 189, 160, 229, 165, 189] （6 字节，每字 3 字节） 统一成字节后，中英文就没区别了 ——都是一串 0-255 的数字，BPE 在这串数字上做合并。

训练的时候，有可能吧中文的部分字节合并到一起，但并不组成汉字，例如 228，189 组合到一起，但是三个字节才能组成汉字，所以这个 token 并不能表示汉字。

在训练阶段我们训练出了 Tokenizer，在之后任何的预训练、 SFT、 DPO、 PPO 推理阶段呢，我们就都只用这个 Tokenizer 模型就可以了。在训练阶段呢，我们让它学会了记很多这个高频的字节合并对，而在使用阶段呢，我们并不需要让它再重新学习了。这些在训练阶段做好的字节合并对（也就是合并规则，例如第一条：228 和 196 合并。第二条：123 和 98 合并）都会保存下来。在编码 Encoder 阶段呢，我们就按照这个字节合并对来依次应用它，把训练时学到的 N 条规则从头到尾的扫一遍。规则是固定的，所以编码过程是确定的。encode、decode 不改变 tokenizer，就是纯函数式，干活的。

BPE 的合并逻辑是 训练时一次性学好的 ，存成 tokenizer.json 里的 6108 条 merges 规则（按频率排序）。 编码时只是"重放"这套规则 ——按顺序扫描，能合并就合并，不能就留字节。训练是"统计生成规则"，编码是"确定性套用规则"，两者用同一套规则，但一个是写入、一个是只读。这就是为什么 tokenizer 训练一次就能终身用——规则学完就固定，编码只是查询和应用。

#### 流程总结

* 训练 ：统计 → 学出 N 条合并规则
* 存储 ：规则存进 tokenizer.json 的 merges 字段
* 编码 ：按顺序重放规则，文本 →id
* 解码 ：id→ 字节串 → 拼接 →UTF-8 解码 → 文本
