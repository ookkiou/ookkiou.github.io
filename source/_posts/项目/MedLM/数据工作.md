选源 → 清洗 → 去重 → 拆分/固定评测集 → 配比 → 格式化 → 偏好对构造（DPO 阶段）→ 防泄漏 → 校验 → 抽检 → 版本化 → 训练

数据工作在后训练里通常占掉一大半的工程时间，业内甚至有个说法叫"data-centric"——模型结构你动不了，数据是你唯一能精雕细琢的原料。现在按一条数据从拿到至进入训练的流水线走一遍，大致是这么几个环节：

**选源与获取。** 先决定数据从哪来：开源数据集（HuggingFace Datasets、领域公开集如 CMB、GSM8K）、用强模型蒸馏生成（self-instruct / Evol-Instruct 那类方法）。或者自建，这种数据开源集里往往没有，恰恰是数据工程上能拿来讲的亮点。

**清洗与过滤。** 把脏的、重复的、低质量的部分去掉。去重一般做两层：精确去重（哈希一致）+ 模糊去重（MinHash/SimHash 找近似重复）；然后按长度、语言混杂、乱码、HTML 残留做规则过滤，讲究一点的再加质量打分（困惑度或小分类器）。这个环节的力度跟阶段成正比：CPT 最严格；SFT 次之；而评测集是反过来要求"干净到可以当标准答案"的。

**格式转换。** 这是最容易踩坑也最"绑定"的一步。原始数据集格式五花八门（alpaca 式的 instruction/input/output、sharegpt 式的多轮对话），而训练时框架要求的是和底座 tokenizer 配套的 messages 格式，最终靠 apply_chat_template 拼成带特殊 token 的文本。比如：

```
# 统一的中间格式
sample = {"messages": [
    {"role": "system", "content": "你是一名严谨的医生"},
    {"role": "user", "content": "布洛芬和对乙酰氨基酚能一起吃吗"},
    {"role": "assistant", "content": "..."},
]}
# 落到具体底座时才绑定模板
text = tokenizer.apply_chat_template(sample["messages"], tokenize=False)
```

注意边界：中间格式（messages）是可迁移的，换底座不用重做；但 chat template、system prompt 习惯、loss mask 怎么处理（只对 assistant 段算 loss）都是绑定具体底座和训练框架的，换 Gemma→Qwen 就要重查一遍。

**配比与混合。** 不是把垂域数据全倒进去就好，要控制垂域数据和通用数据的混合比例，防止灾难性遗忘——"SFT 配比"实验、通用 token 配比，做的都是这件事。它本质上是个要跑消融实验回答的超参数问题。

**按范式构造特殊数据。** 这是三种范式数据需求差异最大的地方，值得单独记：SFT 要 (指令, 回答) 对，量大管饱；DPO 要 (prompt, chosen, rejected) 偏好对，量小但要精——对的来源可以是人标、强模型当裁判、或用 policy 自己采样多个回答再打分排序；而 GRPO/PPO 只需要 prompt 集合加一个能自动判分的奖励函数（数学里就是"抽出最终答案和标准答案比对"），回答是训练时在线生成的，根本不需要标注答案。所以同样做数学，SFT 的数据工作和 GRPO 的数据工作是两种完全不同的活。

**去污染。** 把评测基准的题目从训练数据里剔除，否则评测分数虚高、项目可信度归零。工业界常用 n-gram 重叠检查：

```
def contaminated(train_text, eval_questions, n=13):
    grams = {train_text[i:i+n] for i in range(len(train_text)-n)}
    return [q for q in eval_questions
            if any(q[i:i+n] in grams for i in range(len(q)-n))]
```

**评测侧的数据工作**和训练侧是镜像的：选定 benchmark → 把题目转成模型的 prompt 格式（含 few-shot 样例的摆放）→ 写答案抽取和打分逻辑（正则抽答案、exact match、或模型裁判）→ 有条件的话再自建一个私有评测集，因为公开 benchmark 迟早会被别人的训练数据污染。

最后一个贯穿所有环节的事：**数据版本管理**。每次清洗、配比、去污染之后的数据集都要能复现（记录版本号、数据 hash 写进训练 config），不然消融实验做出来没法归因。
数据版本管理的核心思想就三条：进入训练的每一份数据都是**不可变的快照**（不原地覆盖，改了就生成新版本）；每份快照有**唯一标识**（版本号或内容哈希）；训练记录里**显式指向**这个标识。这样任何一次训练结果都能回答"我是用哪份数据训出来的"。
还有一个比"版本"更完整的概念叫 **lineage（血缘）**：不光记录"这是 v3"，还记录"v3 = 原始数据 v1 + clean.py@某个 git commit + 去重阈值 0.9 + 配比 3:7 生成的"。也就是说版本不止给最终数据集打，流水线的每一步输入输出都打标。这样任何人（包括三个月后的你）能从原始数据逐字节复现出 v3。面试时被问"你的实验怎么保证可复现"，能答到这一层就很加分了。
