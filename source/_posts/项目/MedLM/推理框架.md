推理框架是一类专门用于**模型部署和高效执行**的计算引擎或工具集。
训练框架：PyTorch、tenseflow 等
推理框架：VLLM、SGLang 等
与侧重通过大量数据调整模型参数、追求更高准确率的**训练框架**（如PyTorch、TensorFlow）不同，推理框架的核心目标是**计算效率最大化**。它主要解决三个问题：
- **模型优化**：通过**量化**（如将32位浮点数压缩为8位整数）、**算子融合**（合并多个计算步骤）、**层剪枝**（去除冗余连接）等技术，大幅降低模型的计算量和体积。例如，INT8量化可将模型体积压缩4倍，推理速度提升2-3倍。
- **硬件适配**：自动匹配并充分利用GPU、CPU、NPU（神经网络处理单元）等不同硬件的指令集和架构特性，实现“软硬结合”的最佳性能。
- **服务封装**：提供REST API、gRPC等标准化的网络接口，支持动态批处理（将多个请求合并处理）、模型热更新等企业级功能，方便将AI能力集成到实际应用中。


# VLLM
## PagedAttention
PagedAttentio 是 vLLM 框架的核心创新，它是一种受操作系统**虚拟内存和分页**技术启发而设计的**注意力算法**。

在 LLM 的自回归推理中，为了加速生成，需要缓存之前所有 token 的 Key 和 Value 向量，即 KV Cache。然而 kvcache 的碎片化严重，传统方式要求 kvcache 占用连续的内存空间，于是为了防止内存不足，预留的长度一般都是最大，导致浪费。

PagedAttention 借鉴操作系统的分页思想，将传统的连续内存管理转变为灵活的分块管理：

1. **分块存储 (Block-based)**：将每个请求的 KV Cache 分割成固定大小的 **KV 块 (KV Blocks)**，每个块包含固定数量（如 16 或 32 个）token 的 KV 对。这些块可以在物理内存中**非连续**地存储。

2. **逻辑到物理的映射 (Mapping)**：系统为每个请求维护一个 **块表 (Block Table)**，它就像一个“地址簿”，记录了该请求“逻辑上连续”的块，实际上被映射到哪些“物理上分散”的内存块中。

3. **按需分配 (On-demand Allocation)**：不再需要预先分配好整个序列长度的内存。PagedAttention 会根据生成过程的实际需要，**动态地、按需地**为新的 token 分配物理块。这种机制彻底解决了外部碎片和内存预留浪费的问题。

这样 PagedAttention 就带来了关键优势：

- **极高的内存利用率**：内存浪费从传统方式的 60-80% 骤降至 4% 以下。唯一的微小浪费仅来自每个请求最后一个块中未被填满的部分。
    
- **高效的内存共享**：PagedAttention 支持在不同请求间共享相同的 KV 块。例如，当多个用户请求都包含相同的系统提示词时，只需在内存中保存一份对应的 KV Cache，所有请求共享即可。这种共享使得内存占用减少 55%，吞吐量提升 2.2 倍，在处理并行采样等复杂解码策略时优势尤其明显。
    
- **显著的性能提升**：凭借高效的内存管理，以 PagedAttention 为核心的 vLLM，其吞吐量相比 HuggingFace Transformers 最高可提升 24 倍，相比 HuggingFace TGI 最高可提升 3.5 倍。

PagedAttention 通过将操作系统的分页思想创新性地应用于 LLM 推理的内存管理，将内存视为可按需分配和共享的“块”，极大地提高了 GPU 显存利用效率。

它不仅是一个理论创新，更是目前许多主流推理引擎（如 vLLM、TensorRT-LLM 等）的**标准配置**，是支撑当今大模型高效、低成本服务的关键技术之一。

## sharing KV blocks

KV Block 的共享，在 vLLM 中是通过其 自动前缀缓存 (Automatic Prefix Caching) 机制实现的。这项技术使得具有相同前缀的不同请求，能够共用同一份 KV Cache，从而显著节省显存并避免重复计算。

假设vLLM的**每个KV Block固定包含4个Token**（实际为16或32，这里简化）。现在有两个用户请求，它们共享了非常长的系统指令和背景材料。

### 📝 两个具体的请求

**请求A（用户A问天气）**：

> `[System] 你是客服助手，回答需简洁。参考文档：产品X售价100元，保修2年。` **`用户：产品X保修期多久？`**

**请求B（用户B问价格）**：

> `[System] 你是客服助手，回答需简洁。参考文档：产品X售价100元，保修2年。` **`用户：产品X多少钱？`**

---

### 🔍 前缀识别与分块（Token切分）

为了清晰起见，我们将前缀部分（完全相同的部分）切分成块：

- **Block 0 (逻辑块0)**：`[System] 你是客服助手，回答需简`（前缀开始）
    
- **Block 1 (逻辑块1)**：`洁。参考文档：产品X售价100`（前缀继续）
    
- **Block 2 (逻辑块2)**：`元，保修2年。` （**前缀结束，此处两个请求完全相同**）
    

从“用户：”开始，内容不同：

- **请求A 的 Block 3A**：`用户：产品X保修期多久？`
    
- **请求B 的 Block 3B**：`用户：产品X多少钱？`
    

---

### ⚙️ 物理内存中的共享过程

1. **请求A先到达（预填充阶段）**：
    
    - vLLM 计算 Block 0、1、2 的哈希值，发现缓存中没有。于是在GPU物理内存中**分配三个物理块**（假设物理地址 `P0`、`P1`、`P2`），存入KV Cache，并将哈希值与物理地址记录到全局哈希表。
        
    - 请求A的逻辑块表：`[逻辑0->P0, 逻辑1->P1, 逻辑2->P2, 逻辑3A->P3A(新分配)]`。
        
2. **请求B随后到达（预填充阶段）**：
    
    - 处理 Block 0：计算哈希值，命中全局哈希表，发现已存在物理块 `P0`。**直接复用**，不分配新内存。
        
    - 处理 Block 1：命中，复用 `P1`。
        
    - 处理 Block 2：命中，复用 `P2`。
        
    - 处理 Block 3B：这是新内容，哈希未命中，分配新物理块 `P3B`。
        
    - 请求B的逻辑块表：`[逻辑0->P0, 逻辑1->P1, 逻辑2->P2, 逻辑3B->P3B]`。
        

---

### 📊 结果对比（共享后的状态）

| 物理内存块   | 存储的内容 (Token片段)        | 引用计数  | 被哪些请求使用  |
| ------- | ---------------------- | ----- | -------- |
| **P0**  | `[System] 你是客服助手，回答需简` | **2** | 请求A, 请求B |
| **P1**  | `洁。参考文档：产品X售价100`      | **2** | 请求A, 请求B |
| **P2**  | `元，保修2年。`              | **2** | 请求A, 请求B |
| **P3A** | `用户：产品X保修期多久？`         | **1** | 仅请求A     |
| **P3B** | `用户：产品X多少钱？`           | **1** | 仅请求B     |
### 💎 这个例子揭示的关键优势

1. **显存节省**：前缀 `P0`、`P1`、`P2` 在物理内存中**只保存了一份**，但服务了两个请求。如果前缀长达数千Token，且并发有100个请求，显存占用直接缩减为原来的 **1/100**。
    
2. **计算节省**：请求B在处理前缀时，**完全跳过了P0、P1、P2的注意力计算**（因为KV Cache直接复用），只需计算自己独有的问题部分（Block 3B），首个Token生成（TTFT）速度极快。
    

这就是vLLM通过哈希值识别实现“相同前缀物理共享”的完整工作流程。
